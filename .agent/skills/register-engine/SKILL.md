# W-엔진 등록 스킬

신규 W-엔진을 `engine` 및 `engineCost`에 등록하거나, 명확히 지정된 기존 항목을 보완한다. 이 절차는 특정 모델이나 대시보드 UI에 종속되지 않는다. 현재 에이전트가 제공하는 브라우저·HTTP·파일·PostgreSQL·R2 기능을 사용한다. 레포에서 실행할 때는 [엔진 등록 지식](../../../wiki/operations/engine-registration.md)과 [공통 등록 안전 수칙](../../../wiki/operations/roster-auto-registration.md)도 읽는다. 다른 환경에서 해당 문서를 읽을 수 없으면 이 스킬의 기준을 적용하고, 없는 기능이나 권한을 가정하지 않는다.

## 입력 및 정보 확인

- 사용자가 준 Fandom W-Engine 문서 URL을 메타데이터 취합의 기준으로 삼는다. URL이 없으면 엔진명으로 정확한 문서를 찾아 확인하고, 동명이 문서가 있으면 사용자에게 선택을 요청한다. 예시 페이지: [Bloodmarrow Coffer](https://zenless-zone-zero.fandom.com/wiki/Bloodmarrow_Coffer).
- 문서에서 `nameEn`(페이지 제목), `nameKo`(Other Languages의 Korean 공식명), 등급, 대응 특성, 기본·부가 스탯, 출시 버전·일자, 입수 방식, W-Engine 효과를 읽는다. 스탯·효과·출시 정보 중 DB에 없는 값은 메타데이터 검토 참고로만 사용한다.
- Fandom은 커뮤니티 편집 위키이므로 그 내용을 공식 발표라고 표현하지 않는다. 문서 내용이 모호하거나 사용자 제공값과 충돌하면 해당 차이를 보여주고, 공식 HoYoverse 출처로 확인하거나 질문한다.
- `exclusiveAgentId`, `attributeId`, `isPickup`, `isTeaser`는 문서가 명시하거나 다른 신뢰할 수 있는 근거가 있을 때만 설정한다. “for Armorer”처럼 특성에 속한다는 표기는 전용 에이전트 지정으로 간주하지 않는다. `specialtyId`는 문서의 특성명을 DB `specialty`와 대조해 매핑한다.
- 사용자가 **일러스트와 아이콘 파일 경로 또는 URL을 각각 제공**한다. 두 입력을 하나로 합치거나 서로 바꿔 쓰지 않는다. 로컬 파일이면 존재 여부와 이미지 형식을 확인하고, 원본을 임의로 자르거나 수정하지 않는다. URL이면 해당 역할과 페이지의 이미지 표기를 대조한다.
- 위키 갤러리 파일은 사용자 제공 입력을 대신하지 않는다. 사용자가 해당 갤러리 URL을 직접 제공했다면 그 URL을 그대로 적용한다. CDN 보안 확인 페이지가 나타나도 CAPTCHA를 풀거나 보안 검사를 우회하지 않는다.
- 사용자 입력에 코스트 배열이 있으면 그대로 검토한다. 없으면 엔진 등록 규칙의 등급·픽업별 표준 프리셋을 적용한다. 프리셋이 적용되지 않는 예외는 임의 산정하지 않는다.

## 사전 대조 및 승인

1. 사용 가능한 읽기 전용 DB 연결로 `engine`과 관련 `agent`, `specialty`, `attribute`, `image`, `engineCost` 행을 조회해 기존 ID·이름·외래키·이미지 URL·코스트를 확인한다. 라이브 스키마의 컬럼 타입·NULL 허용 여부·기본값·identity·외래키·고유 제약도 확인한다. 프로젝트 문서와 실제 스키마가 다르면 쓰기 전에 차이를 보고한다.
2. 기존 W-엔진은 이름과 연결 정보를 대조한다. 동일 후보가 여러 개거나 기존 데이터와 충돌하면 쓰기를 멈추고 차이를 보고한다. 기존 행 보완 시 엔진 UUID는 유지한다. 새 행에만 UUID를 생성한다.
3. `rank`의 DB enum과 `image.type`의 실제 enum 라벨을 조회한다. 현재 운영 enum에는 엔진 일러스트 `EngineImage`, 아이콘 `EngineIcon`이 있다. 실제 DB에서 허용되는지 확인하고, 타입이 없으면 스키마를 임의 변경하지 말고 중단한다.
4. 사용자에게 등록·수정할 필드, 연결할 FK, 적용할 1~5돌 코스트, 두 이미지 입력과 업로드 목적지를 요약해 보여주고 명시적 승인을 받는다. 승인은 제안에 적힌 업로드와 데이터 변경에만 적용되며, enum·제약·테이블을 바꾸는 스키마 변경은 별도 승인 대상이다. 승인 전에는 R2 업로드나 DB 쓰기를 하지 않는다.

## 승인 후 반영

- 현재 실행 환경이 제공하는 R2 업로더를 사용해 일러스트 입력을 `engines/banner`, 아이콘 입력을 `engines/icon`에 각각 업로드한다. 이 레포의 CLI 보조 도구를 쓸 수 있으면 로컬 경로는 `--file`, HTTP(S) 주소는 `--url`로 `.cursor/skills/upload-r2-image/scripts/upload.ts`에 전달한다. 이 도구는 `CLOUDFLARE_API_TOKEN`, `R2_ACCOUNT_ID` 또는 `CLOUDFLARE_ACCOUNT_ID`를 요구하며, `R2_BUCKET_NAME`과 `R2_PUBLIC_URL`은 선택값이다. 비밀값은 현재 에이전트 런타임의 안전한 secret 주입 경로로 전달한다. 특정 IDE·모델의 secret 저장소를 가정하거나 `.env`를 읽지 않는다. 필수 값이나 업로드 기능이 없으면 업로드 전에 중단하고 필요한 변수명만 보고한다. 반환된 CDN URL과 R2 key를 기록한다. 하나라도 실패하면 DB 쓰기를 시작하지 않고 이미 성공한 URL을 보존한다.
- 같은 CDN URL이 `public.image`에 있으면 기존 이미지 UUID를 재사용한다. 아니면 UUID를 새로 만들고, 확인한 이미지 타입과 함께 이미지 행을 작성한다.
- 엔진 마스터, 두 이미지 참조, `engineCost`의 `rate = 1, 2, 3, 4, 5` 다섯 행을 한 원자적 DB 작업으로 반영한다. 코스트는 `("engineId", rate)` 기준으로 멱등 처리한다. 실패하면 전체 DB 변경을 롤백하고, 재시도 시 성공한 R2 URL을 재사용해 재업로드하지 않는다.
- 권한이 있는 PostgreSQL 연결을 사용하고 가능한 경우 바인드 변수로 SQL을 실행한다. 엔진·이미지·다섯 코스트 행은 하나의 트랜잭션에 넣는다. 명시적 트랜잭션을 지원하지 않는 Supabase SQL Editor에서는 전체 변경을 단일 `DO $$ ... $$` 문으로 묶어 오류 시 롤백되게 한다. 스키마 DDL은 등록 트랜잭션에 포함하지 않으며, 별도 승인을 받은 변경만 실행한다.

## 완료 검증

읽기 전용 조회로 다음을 확인한 뒤 결과를 보고한다:

- 엔진이 정확히 한 행이고 이름·등급·픽업·전용 에이전트·특성·속성 값이 승인안과 일치한다.
- `imageId`와 `iconImageId`가 각각 올바른 `public.image` 행을 가리키고, 공개 URL과 이미지 타입이 의도한 경로에 대응한다.
- `engineCost`에 해당 엔진의 rate 1~5가 각각 한 행씩 있고 코스트 배열이 승인안과 같다.

업로드 URL, R2 key, DB 결과를 함께 요약한다. 하나라도 검증되지 않으면 완료로 보고하지 않는다.
